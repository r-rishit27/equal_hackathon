Reconciliation architecture: Plan A vs Plan B vs Plan C

Research and bake-off for Reckon.ai's reconciliation workflow builder (PO ↔ audit report ↔ invoice, plus delivery receipts). Prototypes were built and tested on real Bata documents. November 2026.

Recommendation: Plan C (hybrid). All three plans calculate the payable correctly. They differ in what happens after the first run: whether reviewers' decisions survive, whether a past verdict can be replayed, and how many systems must stay up. Plan C was the only plan to pass every test: 16 of 16, against 13 for A and 8 for B.

With a graph database in the stack, the rule that matters is this: the graph can be the place we search for matches, but it must never be the only place a human decision is stored. Plan C follows that rule; Plan B does not.

Assumption for this document: a graph database (e.g. TigerGraph) is part of the stack.

Each plan is described as it would work with one. In the tests the graph was simulated in memory behind the same interface; no real graph database was installed. All of B's failures come from where data lives and what gets deleted, so a real graph database behaves the same way. A real one only adds network time on each query.

1. The three plans

Plan A · "ours"

Relational tables + vocabulary learning

  • Documents, lines and quantities in separate Postgres tables (9 tables, rev 1 schema).
  • Codes enforced by database foreign keys.
  • Two-tier vocabulary loop: unknown column labels are searched in the dictionary. Safe ones are auto-added; anything that affects payment goes to a person.
  • Graph DB role: optional, read-only copy for traversal. Decisions stay in Postgres rows, but they are overwritten in place.
Plan B · engineer's

One JSON row per document + graph as match surface

  • Each document is a single Postgres row; lines and quantities sit inside as JSON.
  • A trigger checks codes inside the JSON.
  • Graph DB role: the core. Line matches are graph edges, and reviewer confirmations and precedents ("memory graph") are stored in the graph.
  • The graph is described as "rebuildable from Postgres". Settled invoices are pruned from it.
  • New client labels are added as manual alias rows.
Plan C · hybrid

JSON row + permanent decision log + graph as a copy

  • Plan B's one-row-per-document storage, but the extraction is never edited.
  • Every human action (confirmed match, correction, precedent) is a new row in an append-only Postgres table, keyed by a stable line ID that survives re-reading the document.
  • Graph DB role: a projection rebuilt from Postgres. It can be wiped and rebuilt with nothing lost, and Postgres SQL can answer the same queries if the graph is down.
  • Plan A's vocabulary loop on top.

2. How we tested

  • Real documents:
    • the Bata purchase order PPO00024046-1 (₹7,54,596, Anjle MEP)
    • the J P Chawla audit report for Thane store 8255
    • Anjle's tax invoice AMP/26-27/070
    • a Safexpress delivery receipt
    • the Matolia Rai audit report for Mangalore store 9621
  • Same inputs and same rules for all three plans. Documents were turned into structured data by script, with no AI calls, so extraction quality is held constant. All plans use one shared rules engine; only storage and decision handling differ.
  • Synthetic data where needed: a goods PO and invoice for the delivery-receipt test, a fictional "client 2", and 1,000- and 10,000-document scale data built from the real line items.
  • Environment: SQLite with JSON support, since no Postgres was installed. The graph was an in-memory stand-in. Nothing was sent outside the laptop.

4. Findings

4.1 Correctness: all three plans are equal

  • Thane payable reproduced exactly by all three: ₹6,06,740.50 payable, ₹30,000 held, ₹1,850 unbilled, ₹6,34,890.50 invoiced. 6,06,740.50 + 30,000 − 1,850 = 6,34,890.50.
  • All 12 expected flags caught by all three:
    • AHU billed as 8.5 TR, but the signed sheet says 7 TR
    • buyer GSTIN typo on the e-invoice (27AABC1043Q1ZM vs 27AABCB1043Q1ZM)
    • 60% advance not netted
    • late-delivery penalty exposure: work evidenced 175 days after the 30-03-2026 due date
    • 3 out-of-audit lines held, including scaffolding with no photo
    • MCP hooter verified but not billed
    • battery count differs between the audit table and the signed sheet
  • Mangalore "rate after 5%": all three paid at the discounted rate, ₹21,29,134.95. Using the list rate would have over-paid ₹93,586.
  • Delivery receipt (POD): all three treated it as proof that 18 packages arrived, never as item counts, and didn't fail the invoice for lacking line items. All three flagged the receiver's stamp address (#10 Temple Road) not matching the consignee (#2951).

4.2 Human decisions: where the plans differ most

  • Re-reading a document after a parser fix: A and B lost 22 of 26 matches a reviewer had confirmed, plus the reviewer's correction. C kept all of them.
  • Graph rebuild (B): 0 of 23 confirmations and 0 of 23 precedents survived. The graph is "rebuildable" from document data, but the decisions were only ever stored in the graph.
  • Pruning (B): once a settled invoice is pruned, its verdict can't be replayed. That defeats the "replay for the auditor a year later" feature.
  • "As of" replay: in A and B, replaying an old run shows today's decisions, not the ones in force at the time. C replays exactly what was recorded.
  • Re-running after a decision: A and B return the old stored result, because the run's fingerprint ignores decisions. C produces a fresh result.
  • A tempting quick fix is unsafe. Carrying decisions forward by line position would have put the battery correction on the wrong line (the MCP hooter) without any warning.

4.3 Running a graph database as a dependency

  • In B, when the graph is down, reconciliation stops and reviewers can't confirm matches. This is by design ("graph unreachable: post nothing").
  • The questions the rules ask are only 1–2 hops (e.g. "how much has been billed against this PO line?"). Postgres SQL gave the same answer in about 1.5 ms.

4.4 Safety of the vocabulary loop

  • When we turned off the rule that payment-related labels need a person, a misleading header ("Qty Verified by Vendor", which is really the vendor's claim) was auto-mapped as the audited quantity. It silently over-paid ₹18,660 on 3 lines. With the rule on, A and C sent it to a person.
  • B silently mapped a bare "QTY" column on a goods receipt to "ordered quantity". The dictionary seeder had created a global entry for that ambiguous word. A and C flag ambiguous words for review.
  • An unknown extra column made B reject the whole document. A and C saved the document and put the unknown column in a review queue with its values.
  • Onboarding effort was similar (5 / 6 / 5 human steps). The loop's value is the safety guard, not saved time.

4.5 Editing and code changes

  • Two reviewers editing different lines of one document: B lost one edit, because the whole document's JSON is rewritten on save. A single-statement update would avoid this.
  • Retiring a code (e.g. a unit): in B, every old document using that code can no longer be corrected. In C, old documents stay editable and only new use is blocked. In A, new documents can still use the retired code.
  • New field such as bin_location: B's claim that it "costs nothing" is false. With strict checks, it is rejected until the dictionary and code are updated. Without them, a misspelling like bin_locaton slips through.

4.6 Problems in the documents themselves

  • Five terms the schemas use are missing from the dictionary: evidence_layer, date_role, quantity_legend, role_alias_raw and RECEIPT_DATE. Seeded as written, all three plans reject the Thane audit report. More kinds and keys are missing too, e.g. the check codes and the signature fields on delivery receipts.
  • Evidence-layer conflict. The agreed ₹6,06,740.50 only comes out if the typed audit table sets the payable. The extraction spec says the signed site sheet should, which gives ₹6,08,143.50.
  • Errors in the engineer's scalability doc:
    • "Six of eight are configuration": the table has 7 rows, of which 5 need no migration.
    • The worked invoice doesn't add up (₹7,49,171.00 vs ₹7,49,170.79).
    • The examples mix a Thane store with a Mysuru delivery and use a different PO number and vendor.
    • Its storage arithmetic is correct, but it doesn't matter at this scale.
  • GSTIN checksum failures: the consignor GSTIN on the delivery receipt, and the dictionary's "corrected" Karnataka GSTIN.

7. Advantages of each plan

Plan A

  • Simplest and fastest analytics: plain SQL across stores.
  • Simultaneous edits to different lines are safe by nature.
  • Database-enforced codes.
  • Least code.
  • Vocabulary loop guards payments.

Plan B

  • Simplest write path: one row per document.
  • Fastest to save and re-read documents.
  • Smallest storage.
  • New fields and quantity types fit without schema changes.
  • Graph makes match traversal natural, with fast in-memory lookups.

Plan C

  • Every human decision is permanent and auditable.
  • Decisions survive re-reads, rebuilds and pruning.
  • Exact "as of" replay for auditors.
  • The graph can be wiped and rebuilt safely, and Postgres covers for a graph outage.
  • Retired codes never freeze old documents.
  • Vocabulary loop guards payments.

8. Weaknesses of each plan

Plan A

  • Decisions and corrections are lost when a document is re-read.
  • Decisions are overwritten in place, so there is no "as of" replay.
  • Re-runs ignore new decisions.
  • Retired codes still accepted on new documents.
  • One rate per line (can't hold list + net rate).

Plan B

  • Graph outage stops payments and reviews.
  • Decisions and precedents are lost on graph rebuild.
  • Pruning breaks replay.
  • Concurrent edits can be lost.
  • Retired codes freeze old documents.
  • Unknown columns block whole documents.
  • Ambiguous labels are mapped silently.
  • Slower analytics.

Plan C

  • Most tables and code.
  • Analytics slower than A without an extra summary table.
  • Slowest reconciliation in this SQLite test.
  • Stable line IDs depend on printed line numbers; if a parser fix changes them, a person must re-confirm (flagged, not silent).

9. Using a graph database safely

If the graph database stays, use it the Plan C way:

  1. Postgres is the source of truth for documents and for every human decision. The graph only holds copies.
  2. Rebuild the graph from Postgres documents and decisions. A rebuild should then produce an identical graph.
  3. Don't block on the graph. If it is down, answer the 1–2 hop questions from a Postgres edges table, or queue without stopping reviews.
  4. Prune only the graph copy, never the history. Replay always reads from Postgres.
  5. Keep precedents ("memory") in Postgres and copy them into the graph for fast lookup.

10. Recommendation and changes needed

  1. Build Plan C. Store extractions as one row per document and never edit them; a re-read creates a new version.
  2. Make decisions permanent. Add append-only tables for corrections, confirmed matches and precedents, keyed by stable line IDs. A missing line becomes a visible "please re-confirm" task.
  3. Treat the graph (or a Postgres edges table) as a rebuildable copy, following section 9.
  4. Include decision history in each run's fingerprint, so re-runs reflect new decisions and replays are exact.
  5. Check codes only on new data or on changed codes, so old documents stay correctable.
  6. Keep the vocabulary loop with its payment guard. Ambiguous words never auto-map, and unknown columns go to a review queue.
  7. Add a summary table of lines for cross-store rate checks and duplicate-billing checks.
  8. Fix the dictionary before seeding: add the missing terms and stop global entries for ambiguous words.
  9. Decide which evidence layer pays: the typed audit table or the signed site sheet.

11. Open questions and what is untested

  • Business decision: does the typed audit table or the signed site sheet set the payable? (₹6,06,740.50 vs ₹6,08,143.50)
  • Data check: confirm the two GSTINs that fail the checksum against Bata's master data.
  • Real Postgres: not tested (none installed). Worth a quick re-run to confirm storage sizes and whether B/C's slower reconciliation was a SQLite effect.
  • Real graph database: not tested. It wouldn't change B's design failures and would only add network time.
  • AI extraction and AI judge: not tested, since no external calls were allowed. This doesn't affect the storage choice, but it matters for how often the vocabulary loop maps labels correctly. It needs approval to use client documents and about 200 labelled examples.
  • Lines without printed numbers (some invoices, emails): how should stable line IDs be formed?
