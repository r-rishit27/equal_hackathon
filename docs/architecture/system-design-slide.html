Reckon.ai System design · one page · branch dev

One Postgres instance, four processes, and every route pinned to a tenant

Reckon.ai runs payables, receivables and working capital for Indian finance teams. The architecture is deliberately small: a React workspace, one FastAPI app, one pipeline process of twelve change-data-capture workers, and PostgreSQL as both the store and the event bus — no Kafka, no queue broker. Everything that leaves the VPC is a named provider with a named failure mode. Select any box to see what it does and where it lives.

A record is promoted, never trusted on arrival

raw_→ stg_→ fact_

Staging is a validation buffer: a row reaches fact_* only after dedup and field validation. An exact DUPLICATE blocks promotion and forces sync_status = ERROR. A soft duplicate flags REVIEW and promotes anyway — a vendor legitimately re-issues a monthly retainer at the same amount, and blocking those would reject more good bills than bad ones.

Two Tally modes, one set of tables

Server-side pull (TallyReadWorker over the XML socket) and agent push (OnsummTallyAgent.exe on the customer's machine) write the same stg_invoices, stg_bills, stg_payments with identical upsert logic. Nothing downstream knows which mode ran. The agent pairs once with a short-lived token, exchanges it for an API key, and only the SHA-256 hash is ever stored.

What the structure still owes

  • 85 connection acquisitions with no finally — watch db_pool_connections_in_use climb and never return.
  • Per-process caches in core/ still block a second API replica.
  • migrations.py runs 26 DDL steps in-process on every boot.
  • Per-environment payment caps live bank-side only, not at the application layer.
